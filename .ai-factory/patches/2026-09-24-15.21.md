# Output changed from one file per resource to one JSON array per resource type

**Date:** 2026-09-24 15:21
**Files:** internal/storage/storage.go, internal/extractor/extractor.go, internal/asanatest/server.go, cmd/asana-extractor/main_test.go, internal/storage/storage_test.go, internal/extractor/extractor_test.go, README.md
**Severity:** medium

## Problem

The user wanted all users in one file and all projects in one file as JSON arrays. The tool wrote `output/users/<gid>.json` and `output/projects/<gid>.json`, one object per file, which is what the original exercise spec asked for.

## Root Cause

A requirements change, not a logic error. The original spec said "each file must contain one resource object, not an array", and storage was built around per-resource upserts (`Store.Put(kind, gid, v)`), so a whole listing could not be written as a single unit.

## Solution

- Replaced `Store.Put` with a streaming `ArrayWriter` (`Store.Begin(kind)` → `Add` per element → `Commit` / `Abort`).
- Elements are written to a temp file in the output dir as pages arrive, so memory stays bounded by one page.
- `Commit` closes the array, fsyncs it and renames it over `<kind>.json`, or discards it when the SHA-256 matches the existing file.
- A failed listing aborts the writer, which removes the temp file and keeps the previous file.
- The extractor now uses one generic `extractKind[T]` per resource type.
- Deleted resources now drop out of the array on the next successful run (no stale files).

## Prevention

- When output granularity might change, keep the writer as a streaming sink (open, append, commit) rather than per-item upserts; both layouts then fit behind it.
- Regression tests should check the observable output layout (exact directory listing and file contents), which is what made this change fail loudly first.
